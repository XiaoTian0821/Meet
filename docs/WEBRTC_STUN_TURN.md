# ConnectMeet — WebRTC, STUN/TURN & Scaling Guide

## 1. How audio/video actually flows

ConnectMeet uses a **peer-to-peer mesh**. For every pair of participants, the browser creates an `RTCPeerConnection` and sends media **directly** between the two machines over UDP (with TCP fallback). PHP is **not** in the media path — it only carries **signaling** (SDP offer/answer and ICE candidates) so the two endpoints can find each other.

```
Participant A ────(UDP media)──────► Participant B
      │                                   │
      └──── signalling via PHP (HTTP) ───┘
```

### Bandwidth scaling (why the mesh has a ceiling)
In a mesh of N participants, each endpoint sends **N−1** video streams. Uplink per participant grows linearly with N, and total network media traffic grows as **O(N²)**. This is why the prototype caps the room at a small number (default 12, configurable in `config/database.php → app.meeting.max_participant_limit`).

> The mesh does **not** promise every network can connect directly. Symmetric NATs, restrictive firewalls, and corporate proxies can prevent a direct UDP connection. STUN helps, but it is not sufficient for all topologies — see §3.

## 2. STUN

**STUN** (Session Traversal Utilities for NAT) lets a host discover its *public* IP/port mapping as seen from outside its NAT. It does not punch holes; it just reports addresses.

ConnectMeet ships with public Google STUN servers by default:
```json
"ice_servers": [
  { "urls": ["stun:stun.l.google.com:19302", "stun:stun1.l.google.com:19302"] }
]
```
These are safe to expose to the browser (they're public). For production you should self-host STUN and/or a TURN server.

## 3. TURN (required for restrictive networks)

**TURN** is a relay that forwards UDP (and TCP) between two endpoints when a direct connection cannot be established. You need TURN when participants are behind **symmetric NATs** or strict firewalls.

### Provisioning a TURN server
1. **Run `coturn`** on a public server (or use a hosted TURN provider).
2. Create a dedicated user + credential.
3. Allow traffic on `3478` (UDP + TCP) in the firewall.
4. Add it to `config/database.php`:
```php
'webrtc' => [
    'ice_servers' => [
        [ 'urls' => [ 'stun:stun.l.google.com:19302' ] ],
        [
            'urls' => [
                'turn:turn.yourdomain.com:3478?transport=udp',
                'turn:turn.yourdomain.com:3478?transport=tcp',
            ],
            'username'   => 'connectmeet',
            'credential' => 'turn-secret',
        ],
    ],
],
```
> The credentials are delivered to the browser in the **public** ICE config. This is acceptable for STUN; for TURN use short-lived, per-user credentials (generated by your app) in a production system rather than a static shared secret.

### NAT reachability checklist
| Network type | STUN alone | TURN needed |
|---|---|---|
| Home / simple NAT | ✅ usually | rarely |
| Office / corporate NAT | ⚠️ often blocked | ✅ likely |
| Mobile (LTE) | ⚠️ varies by carrier | ✅ likely |
| Symmetric NAT | ❌ no | ✅ yes |
| Different public subnets, open UDP | ✅ usually | rarely |

Always document to your users that **cross-network meetings may require TURN** and that not every network can be reached.

## 4. Secure signaling transport

Signaling (credentials, chat, SDP/ICE) must travel over **HTTPS** in any deployed environment so that:
- Meeting credentials and host tokens cannot be sniffed.
- Camera/mic access is allowed (HTTPS is a secure context).

Locally, `http://localhost` is a secure context, so media works while signaling uses `http://` (acceptable for development). In production, enable TLS and set `cookie_secure = true`.

## 5. Connection recovery & cleanup

The JS engine (`assets/js/webrtc.js`) handles:
- **Offer/answer with glare avoidance** — the lower participant id offers, the higher answers.
- **Pending ICE** — candidates arriving before the remote description is set are queued and flushed once `setRemoteDescription` completes.
- **Failed-connection recovery** — on `connectionState === 'failed'`, the peer is closed and re-created.
- **Renegotiation** — when local tracks change (camera toggle, screen share), senders are replaced and a fresh offer/answer round runs.
- **Teardown** — on leave, all peer connections and media tracks are closed and stopped.

## 6. Upgrade path to an SFU (future)

The mesh is a learning prototype. For **large meetings**, replace the mesh with a **Selective Forwarding Unit (SFU)**:

- **mediasoup** (Node.js), **Janus** (C), or **WebRTC-RTU / SRS** are the common choices.
- An SFU sits between peers: each participant sends **one** uplink to the SFU and receives **selected** downlinks, reducing per-user bandwidth from O(N) to O(1) and improving scalability.
- **PHP cannot be an SFU** — it is a request/response web language, not a real-time media server. An SFU must run as a persistent process (ideally on a VPS or dedicated media host).
- The signaling layer can remain PHP; the media path simply targets the SFU instead of peers.

Documented here **as an upgrade path only** — it is **not** implemented in this prototype, and no claim of a working SFU is made.

## 7. Known media limitations (honest)

- **Record** captures the **local** browser's mixed media only — it is *not* a server-side composite of all participants.
- **Captions** use the Web Speech API and reliably caption the **local microphone** only; remote participants' speech is **not** captioned in the mesh prototype (no server-side STT pipeline). The UI discloses this instead of fabricating remote captions.
- **Screen share** respects the browser's explicit-permission model; it never captures the screen silently.
